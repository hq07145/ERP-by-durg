## 4. Step 3: Actionable Recommendations

### Recommendation 1: Archiving Historical Test Notifications (Non-Destructive)
**Do NOT `DELETE` historical records.** Permanent deletion breaks foreign keys, destroys auditability, and alters historical notification counters.
Instead, use **Option A (Dedicated Archive Table)** or **Option B (Archived Tag)**:

#### Option A: Dedicated Archive Table (`archived_notifications`) — Recommended for Cleanest Separation
1. Create `archived_notifications` table mirroring `notifications` structure.
2. In a single atomic transaction, copy the 472 test records into `archived_notifications` and remove them from active `notifications`.
3. The active `notifications` table immediately drops from 1,228 to **756 records** (740 live + 16 uncertain), leaving active tables pristine.

#### Option B: Soft-Archive Column (`is_archived` / `is_test`)
1. Add `is_test BOOLEAN DEFAULT FALSE` column to `notifications`.
2. Update the 472 test records: `SET is_test = TRUE`.
3. Filter in queries: `WHERE is_test = FALSE`.

---

### Recommendation 2: Hiding Test Notifications from Normal Business Users
To prevent business users (Shaikh Sohel, Sachin Bari, etc.) from seeing test alerts in the Bell Popover or on `/notifications`:
1. **Server Action Filter:** Update `getNotifications()` in `app/src/lib/notifications/actions.ts` to exclude records where `is_test = TRUE` (or use Option A where test rows are in `archived_notifications`).
2. **Unread Count RPC Filter:** Update `get_unread_notification_count` RPC to ignore archived/test rows so the bell badge accurately reflects only real commercial unread alerts.
3. **Super Admin Archive UI:** Add a toggle in *System Settings → Notifications* labeled *"Show Archived System Test Alerts"* accessible only to Super Admin for historical compliance inspection.

---

### Recommendation 3: Preserving Historical Audit Information
1. Retain all original UUIDs, timestamps, idempotency keys, and recipient mappings in the archive.
2. Maintain an audit manifest mapping each test batch to its originating test script (as cataloged in Section 2A).
3. If compliance or accounting reviews why an order number is missing in sequence (e.g. `ORD-000011`), the archived notifications provide cryptographic timestamp proof of when the document was generated and subsequent cancellation/purging.

---

### Recommendation 4: Preventing Future Automated Tests from Polluting Production History
1. **Dedicated Test Business Isolation:** All test scripts (`app/scripts/test_*.js`) must run under an isolated test business ID (e.g., `00000000-0000-4000-8000-000000000001`) rather than the active production tenant `11111111-1111-4111-8111-111111111111`.
2. **Automated Notification Mocking in CI/CD:** Add an environment variable `SUPPRESS_NOTIFICATIONS=true` or `IS_E2E_TEST=true` to the test runner harness. When set, `broadcastNotification` short-circuits or writes to `archived_notifications` with `is_test: true`.
3. **Automated Cleanup Hook:** Any script that creates ephemeral orders (e.g. `TST-DLV-...`) must include a `finally` teardown block that deletes its notifications using their unique idempotency key prefix before process termination.
